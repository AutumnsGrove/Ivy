# C3 — the outbox op states (2026-10-04, revised after review)

Gate C3 in `docs/CHUNK3-BRIEF.md`: **before coding the outbox**. It answers four questions — the op
states, which step is durable, the idempotency key, and what happens on a crash after the IMAP ack
and before the DB write. Nothing here is implemented yet.

**Status: reviewed.** DeepSeek wrote the first draft; Claude reviewed it against `ARCHITECTURE.md`
section 4, the round 37 rules and the sync code, found six defects (listed under "What the review
changed"), and this is the corrected design. The operator's answers are in `qa-log.md` round 46.
3d starts only on an explicit "go".

## What 3d covers

The reader actions — flag, archive, delete, mark spam / not junk, and empty Trash — as IMAP-first
writes through one `outbox` table in `state.db` (locally owned, backed up). `STORE`, `MOVE` and
`EXPUNGE` only; compose and `APPEND` are chunk 4. Tags (`$ivy-<slug>`) are 3e and are another op kind
over STORE. The constraints this must keep are already settled and are not reopened here: writes go
to IMAP first; a failed or unconfirmed call never leaves a DB-only change; sync defers to a row with
a non-terminal op; reads never join the outbox; nothing is ever erased; the UI is optimistic and
rolls back.

## Confirmation and undo (operator decision, round 46)

CLAUDE.md rule 6: nothing sends, deletes or moves without an explicit confirmation.

- **Flag and unflag** (read, starred) change no folder and erase nothing: no confirmation.
- **Archive, delete (move to Trash), mark spam, not junk** are moves: a **confirmation modal comes
  before the op is enqueued**. An undo toast is not a confirmation.
- **Empty Trash** (the only `expunge`) gets a stronger modal that states how many messages, and is
  refused outright for any folder that is not the Trash role.
- **Undo is an inverse op, not a hold-back.** After a confirmed move is dispatched, the toast offers
  Undo, which enqueues the opposite move (destination back to source) as an ordinary op, behind a
  confirmation only if it would itself be a delete. Nothing is delayed to make undo possible, so an
  action takes effect at once and the queue has one rule.
- **`cancelled`** therefore means only "superseded before dispatch": a flag followed by its own
  unflag while both are still `pending` collapse to nothing (both become `cancelled`); a later op
  for the same message never reorders an earlier one that is `in_flight`.

## The op row

One row per action, in `state.db`:

| column | meaning |
|---|---|
| `id` | op id (injected ids, not random in production paths) |
| `account_id` | whose mailbox |
| `seq` | monotonic per account, so FIFO is deterministic |
| `kind` | `flags` \| `move` \| `expunge` |
| `content_key` | stable identity of the message; survives a UIDVALIDITY reset |
| `source_folder_id` | **part of the op's identity** (below), not a hint |
| `expect` | the intended postcondition, as canonical JSON (sorted keys): dest folder, flags to add and clear |
| `source_uidvalidity`, `source_uid` | the message actually acted on, set in the same commit that makes the op `in_flight` |
| `state` | the op state (below) |
| `attempts`, `next_attempt_at` | retry bookkeeping |
| `last_error_code`, `last_error_detail` | the reason shown in the UI |
| `idempotency_key` | partial-unique (below) |
| `created_at`, `updated_at`, `completed_at` | times |

**The op names a postcondition, not a command.** It says "the message with content key K in folder F
is in Archive and not in F", not "run `UID MOVE 41 Archive`". The UID is resolved at dispatch, never
at enqueue.

**A message is identified by `(content_key, source_folder_id)`, never the content key alone.** N8
means identical Message-IDs share a content key, and mail you send yourself or Bcc lives in INBOX and
Sent under one key. An Archive of the INBOX copy must never act on the Sent copy, so resolution looks
only inside the named folder, and sync's "defers to the outbox" applies only to the rows of that
content key **in that folder**.

## Dispatch: resolving the message

The worker resolves the UID on the connection, not from the mirror alone:

1. `SELECT` the source folder and compare its UIDVALIDITY with the mirror row's. If it is the same,
   use the row's UID.
2. If it changed (the folder was rebuilt since the row was written), the stored UID may name a
   different message. Re-resolve by `UID SEARCH HEADER Message-ID` inside that folder. Exactly one
   hit: use it. None: the op ends `failed` with `message_gone`. More than one: `failed` with
   `ambiguous` (the operator is shown it; Ivy does not guess).
3. If the mirror has no row for the message in the folder yet (an undo right after a move, before
   sync has mirrored the destination), step 2's search is the resolution.
4. The resolved `(uidvalidity, uid)` is written to the op in the same transaction that sets
   `in_flight`, so recovery asks about that one message.

Before sending, a `pending` op also checks its own postcondition (the message is already not in the
source and a copy is in the destination): if it already holds, the op is `done` without a command.
That is what makes a restored older `state.db`, which can carry a `pending` op the server already
applied, safe.

## Op states

```
pending ──dispatch──▶ in_flight ──ack──▶ done
   ▲                     │
   └──transient fail─────┘        └──postcondition already holds──▶ done
   │
   └──superseded──▶ cancelled
   └──permanent reject / cap reached──▶ failed
```

- **pending** — committed, not yet sent. A fresh op or a retry after a transient failure. Sync
  defers to the row.
- **in_flight** — committed before the command goes on the wire, so it means *may have been sent,
  ack unknown*. Sync defers to the row. (`pending` means *never sent*.)
- **done** — the server acked and the mirror was updated. Terminal.
- **failed** — rejected, unreachable postcondition, or a retry cap reached; terminal until the user
  retries or dismisses; never silently dropped.
- **cancelled** — superseded before dispatch (above). Terminal.

`done`/`failed`/`cancelled` are the "terminal" states; everything else defers sync.

## Which step is durable

1. **Enqueue is durable.** The op row is committed to `state.db` before the API reports the action
   accepted. Enqueue changes nothing on the server and nothing in the mirror: the optimistic state
   lives in the client, which keeps its overlay until the op is terminal (an `outbox.state` hint
   must not flash the old state back on a refetch).
2. **`pending → in_flight` is durable, committed before the command goes on the wire**, together
   with the resolved `(uidvalidity, uid)`. After a crash, "we may have sent it" is distinguishable
   from "we never did".
3. **The mirror update is idempotent and runs before `done`.** The op is in `state.db` and the mirror
   in `mirror.db`, two files, so they cannot share a transaction. The order is: ack, mirror update
   (idempotent: first-wins disable, flag set), then `in_flight → done`. A crash between the last two
   leaves `in_flight`; recovery re-applies the mirror update, which is a no-op if it already ran.
4. **Terminal rows are pruned after seven days** (a constant), so the undo toast and a short history
   survive a restart. Pruning is the only deletion and touches only terminal rows.

## The mirror update

The outbox never writes a destination row. After a `move` ack it hides the **source** row through the
same function sync's disable path uses (`disableRef`: the bytes are copied into the blob store first,
then `DisableMessage` with reason `moved`, first-wins), and the sync pass the `message.changed` hint
triggers mirrors the destination copy by QRESYNC. A `flags` ack sets the flags on that row
(`SetMessageFlags`). An `expunge` ack hides the row as `server_removed`, again through the shared
function. Whichever of the outbox and a concurrent sync pass disables the row first wins, and the
settle step converges on `moved` either way.

## Idempotency key

```
idempotency_key = SHA-256(account_id ‖ kind ‖ content_key ‖ source_folder_id ‖ canonical(expect))
```

The unique index is **partial: only over non-terminal ops** (`WHERE state IN ('pending','in_flight')`).
A double-tap or a retried HTTP request while the first op is still live is a no-op that returns the
existing op. A terminal row never blocks a later op: flag, unflag, flag again must work, and a
whole-row unique index would have made the third tap silently do nothing.

## Crash after the IMAP ack and before the DB write

The window is between the ack and the `done` commit. The op is `in_flight`, with the resolved
`(uidvalidity, uid)` recorded. On restart the worker does **not** blindly re-send and does **not**
assume success: it verifies against the server, on a fresh connection, and only then decides.

For `move`:

1. `SELECT` the source folder.
2. **UIDVALIDITY unchanged and that UID is still in the source** → the command did not apply. Reset
   to `pending`; the next dispatch sends it. No loss.
3. **UIDVALIDITY unchanged and the UID is gone** → search the destination for the Message-ID.
   Found: the move applied and the commit was lost. Apply the mirror update exactly as a fresh ack
   would and mark `done`. Not found anywhere: the server changed under us; mark `failed`
   (`message_gone`), the UI rolls back, and the next sync disables the row as `server_removed`.
4. **UIDVALIDITY changed** → the UID proves nothing. Search the Message-ID in the source and the
   destination: source only → not applied, reset to `pending`; destination only → applied, `done`;
   neither → `failed`; both → `failed` (`ambiguous`). Ivy does not guess.

A copy that was already in the destination before the move does not fool this check, because step 2
looks at the specific message first. If someone else deleted the source and a duplicate sits in the
destination, the postcondition (gone from the source, present in the destination) holds, so `done` is
the right answer.

For `flags`, the postcondition is the flag set; the check is `UID FETCH FLAGS` and re-sending is
idempotent anyway. For `expunge`, the postcondition is the UID absent; a re-issued `UID EXPUNGE` on an
absent UID is a no-op.

The same verify-then-act runs on any error after `in_flight`, not only a crash, so an error in the
mirror update and a `kill -9` recover the same way.

## Capabilities

- **`move` needs the `MOVE` capability** (RFC 6851). Without it the op ends `failed` (`unsupported`).
  Ivy does not emulate it with `COPY` + `STORE \Deleted` + `EXPUNGE`: that sequence is not atomic and
  can lose mail. Purelymail advertises `MOVE`.
- **`expunge` needs `UIDPLUS`** (`UID EXPUNGE`). A plain `EXPUNGE` would also remove other clients'
  `\Deleted` mail, so without `UIDPLUS` the op ends `failed` (`unsupported`). Purelymail advertises it.
  An `expunge` is `UID STORE +FLAGS.SILENT (\Deleted)` then `UID EXPUNGE`, and the API only accepts it
  for messages in the Trash-role folder.

## Failure, retry and rollback

An IMAP `NO` is ambiguous, so classification goes by response code:

| outcome | codes | result |
|---|---|---|
| permanent | `[NONEXISTENT]`, `[TRYCREATE]`, `[OVERQUOTA]`, `[NOPERM]`, `[CANNOT]`, `[CLIENTBUG]`, an unsupported capability | `failed` with the reason; the UI rolls back |
| transient | connection drop, timeout, stall guard, `[UNAVAILABLE]`, `[SERVERBUG]`, `BYE`, a `NO` with no code | back to `pending` with backoff |
| `in_flight` + any rejection | — | run the recovery check first; never permanent on its own |

Limits (constants, in the STANDARDS limits table when 3d lands):

| limit | value | beyond it |
|---|---|---|
| attempts per op | 8 | `failed` (`retries_exhausted`) |
| age of a non-terminal op | 24 h | `failed` (`expired`) |
| backoff | 5 s doubling to 15 min, ±20% jitter | — |
| non-terminal ops per account | 500 | enqueue refused (`outbox_full`) |
| terminal retention | 7 days | pruned |
| IMAP silence on the outbox connection | 2 min (the sync stall guard) | transient |

## Ordering and ownership

One outbox worker per account, one in-flight op at a time, FIFO by `seq`, with the same owner/cancel
discipline as the sync worker. **It owns its own connection**, dialled when the queue becomes
non-empty and closed after the queue has been empty for 60 seconds, carrying the same stall guard.
It never shares the sync worker's connection: that one is owned by the sync worker and spends its life
in IDLE, and a connection with two owners breaks "no goroutine without an owner". Serialising removes
move/move and flag/move races for a single operator and keeps recovery per-op simple. A later op for
the same message resolves its current folder at dispatch, so a chain (archive, then flag) works.

## What C4 will test

A failure-injection test that kills the process between the ack and the mirror update (a fake server
that acks then drops, repeated over many seeds) and restarts the outbox, asserting: the message moved
exactly once, no duplicate row, no lost flag, the mirror converges to the server, and the op ends
`done`. Plus, from the review:

- a message in INBOX **and** Sent under one Message-ID: archiving the INBOX copy leaves Sent alone;
- flag, unflag, flag again: all three take effect (the partial unique index);
- a UIDVALIDITY change while an op is `pending` and while it is `in_flight`: it acts on the right
  message or fails, never on a different one;
- the postcondition already holding on a `pending` op (a restored older `state.db`): `done`, no command;
- the retry cap, the age cap and the queue cap each end in a visible `failed` or a refused enqueue;
- a server without `MOVE` or without `UIDPLUS` fails the op instead of emulating it;
- `expunge` outside the Trash folder is refused.

The fake must be extended with an "ack then kill" fault (the brief says extending `mailworld` is part
of the work). Passing it is gate C4.

## What the review changed

Six defects in the first draft, fixed above (logged in `papercuts.md` as #79-#84):

1. The idempotency key was unique over every row, so a repeated action (flag, unflag, flag) was
   swallowed by the finished first one. It is now partial over non-terminal ops.
2. "The mirror update and `done` are one transaction" is impossible across `mirror.db` and
   `state.db`; the order is now ack, idempotent mirror update, then `done`.
3. The source folder was only a hint, so an Archive could act on a same-Message-ID copy in another
   folder (Sent). It is part of the op's identity.
4. Recovery by content key could be fooled by a pre-existing copy, and a UIDVALIDITY change could
   point a stored UID at a different message. The resolved `(uidvalidity, uid)` is recorded at
   `in_flight`, and every recovery step asks about that message first.
5. Retry was unbounded and every `NO` was a retry; there are now attempt, age and queue caps and a
   response-code classification.
6. `cancelled` was nearly unreachable and undo undefined: undo is an inverse op, `cancelled` means
   superseded, and moves need a confirmation modal (operator decision).

Also corrected: the `in_flight` wording, the sync-connection reuse (now its own owned connection),
the capability requirements, and reusing sync's `disableRef` so a hidden row still gets its
blob-store copy.

## Questions that were open, now answered

1. **What is the reader's delete?** `move` to the Trash role; `expunge` only for emptying Trash.
2. **Terminal retention:** 7 days.
3. **Connection for the outbox:** its own, not the sync worker's (reviewer's change).
4. **One in-flight op per account:** yes.
