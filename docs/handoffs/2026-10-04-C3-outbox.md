# C3 — the outbox op states (2026-10-04)

Gate C3 in `docs/CHUNK3-BRIEF.md`: **before coding the outbox**. It answers four questions — the op
states, which step is durable, the idempotency key, and what happens on a crash after the IMAP ack
and before the DB write. Nothing here is implemented yet; this file is the design to review. 3d
starts only after an explicit "go".

## What 3d covers

The reader actions — flag, archive, delete, mark spam / not junk — as IMAP-first writes through one
`outbox` table in `state.db` (locally owned, backed up). `STORE`, `MOVE` and `EXPUNGE` only; compose
and `APPEND` are chunk 4. Tags (`$ivy-<slug>`) are 3e and are another op kind over STORE. The
constraints this must keep are already settled and are not reopened here: writes go to IMAP first; a
failed or unconfirmed call never leaves a DB-only change; sync defers to a row with a non-terminal
op; reads never join the outbox; nothing is ever erased; the UI is optimistic and rolls back.

## The op row

One row per action, in `state.db`:

| column | meaning |
|---|---|
| `id` | op id (injected ids, not random in production paths) |
| `account_id` | whose mailbox |
| `seq` | monotonic per account, so FIFO is deterministic |
| `kind` | `flags` \| `move` \| `expunge` |
| `content_key` | stable identity; survives a move and a UIDVALIDITY reset |
| `source_folder_id` | where it lived at enqueue (a hint, re-resolved at dispatch) |
| `expect` | the intended postcondition, as JSON: dest folder, flags to add/clear |
| `state` | the op state (below) |
| `attempts`, `next_attempt_at` | retry bookkeeping |
| `last_error_code`, `last_error_detail` | the reason shown in the UI |
| `idempotency_key` | unique (below) |
| `created_at`, `updated_at`, `completed_at` | times |

**The op names a postcondition, not a command.** It says "content key K is in Archive and not in
INBOX", not "run `UID MOVE 41 Archive`". The UID, the folder id and even the row are resolved at
dispatch time from the live mirror, so a move that changed the UID, or a sync that re-numbered the
folder, does not invalidate a queued op. The `source_folder_id` is only a hint for ordering and for
the "which copy" question when a content key has more than one row (N8).

## Op states

```
pending ──dispatch──▶ in_flight ──ack──▶ done
   ▲                     │
   └──transient fail─────┘        └──postcondition already holds──▶ done
   │
   └──user undo / superseded──▶ cancelled
   └──permanent reject──────────▶ failed
```

- **pending** — committed, not yet sent. A fresh op or a retry after a transient failure. The state
  sync defers to.
- **in_flight** — the command has been written to the socket; the ack is unknown. The state sync
  defers to.
- **done** — the server acked and the mirror was updated. Terminal.
- **failed** — the server rejected the action and the postcondition does not hold. Terminal until
  the user retries or dismisses; never silently dropped.
- **cancelled** — the user undid before dispatch, or a newer op makes it moot. Terminal.

`done`/`failed`/`cancelled` are the "terminal" states; everything else defers sync.

## Which step is durable

1. **Enqueue is durable.** The op row is committed to `state.db` before the UI reports the action
   accepted. Enqueue alone changes nothing on the server — the optimistic UI lives in the client,
   the mirror is untouched.
2. **`pending → in_flight` is durable, committed before the command goes on the wire.** This is the
   important one: after a crash, "we may have sent it" must be distinguishable from "we never did".
   An `in_flight` row means *sent, ack unknown*; a `pending` row means *never sent*.
3. **The mirror update and `in_flight → done` are one mirror transaction, committed after the ack.**
   The DB either reflects the effect or it does not; there is no halfway state.
4. **Terminal rows are pruned after a bounded window** (a constant, so the undo toast and a short
   history survive a restart). Pruning is the only deletion and touches only terminal rows.

## Idempotency key

```
idempotency_key = SHA-256(account_id ‖ kind ‖ content_key ‖ source_folder_id ‖ expect)
```

A unique index on the key makes a double-tap or a retried HTTP request a no-op: the insert is
`ON CONFLICT DO NOTHING` and the existing op is returned. Because the key is a *postcondition* and
not a wire command, it does not change when a UID changes. Applying an op whose postcondition already
holds is a pure no-op, which is what makes recovery safe.

## Crash after the IMAP ack and before the DB write

The window is between step 3's ack and step 3's transaction. The op is `in_flight`. On restart the
worker does **not** blindly re-send and does **not** assume success: it verifies the postcondition
against the server and only then decides.

For `move` (Archive, say):

1. Read the live folders for the content key (a targeted `UID SEARCH`/`FETCH` on the source and
   destination).
2. **K is in Archive and not in INBOX** → the ack was received by the server but the commit was
   lost. Update the mirror exactly as a fresh ack would (disable the source row as `moved`, write the
   destination row, tags follow the content key), mark `done`. No second MOVE.
3. **K is still in INBOX** → the command did not apply (the connection dropped before the server got
   it). Reset to `pending` and let the next dispatch send it. No loss.
4. **K is nowhere** → the server changed underneath us. Mark `failed`; the optimistic UI rolls back
   and the next sync disables the row as `server_removed`. Nothing is written that the server does
   not agree with.

For `flags`, the postcondition is the flag set; the check is a `FETCH FLAGS` and re-sending is
idempotent anyway. For `expunge`, the postcondition is the UID absent from the folder; a re-issued
`UID EXPUNGE` on an absent UID is already a no-op.

The same verify-then-act runs on any error after `in_flight`, not only a crash, so an error in the
mirror transaction and a `kill -9` recover the same way.

## Failure and rollback

- **Transient** (network, drop, 4xx, timeout): back to `pending` with bounded exponential backoff
  and jitter; `outbox.state` hints the UI, which shows a quiet "will keep trying". The op survives a
  restart because it is in `state.db`.
- **Permanent** (`pending` op rejected, or the postcondition is unreachable): `failed`, the UI rolls
  back with a reason, and the op stays until retried or dismissed.
- **`in_flight` + rejection**: never treated as permanent on its own; run the postcondition check
  first. This is the rule that stops an already-applied move from looking like a failure.

## Ordering and ownership

One outbox worker per account, one in-flight op at a time, FIFO by `seq`, with the same
owner/cancel discipline as the sync worker. Serialising removes move/move and flag/move races for a
single operator and keeps the recovery logic per-op simple. A later op for the same content key
resolves the row's current folder at dispatch, so a chain (archive, then flag) works.

## What C4 will test

A failure-injection test that kills the process between the ack and the DB transaction (a fake
server that acks then drops, repeated over many seeds), then restarts the outbox and asserts: the
message moved exactly once, no duplicate row, no lost flag, the mirror converges to the server, and
the op ends `done`. The fake must be extended with an "ack then kill" fault (the brief says
extending `mailworld` is part of the work). Passing that is gate C4.

## Open questions for the review

1. **What is the reader's "delete"?** Recommendation: `move` to the Trash role, with `expunge`
   reserved for emptying Trash, so a single tap can never erase mail. If it should instead be
   `\Deleted` + `UID EXPUNGE`, say so before 3d.
2. **Terminal retention.** Recommendation: keep terminal rows 7 days, then prune, so the undo toast
   and a short diagnostic history survive a restart.
3. **Postcondition reads on recovery** need a connection; recommendation is to reuse the account's
   sync connection when the outbox has one, rather than opening a third.
4. **One in-flight op per account** (recommended) versus per folder. The single-operator volume does
   not need per-folder parallelism.
